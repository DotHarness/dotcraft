# Agent 团队

交给 DotCraft 一个复杂请求，它会派一支小队来做。Team Leader 把请求拆成一块任务板，并行分派给一支固定的专家小队——Explorer、Builder、Reviewer、Operator——再把各自的结果汇总成一份完整的答复。你只提一个需求，拿回的是做完的 Mission，而不是一堆要自己盯的子任务。

Agent 团队由内置插件 `agent-teams` 提供。在 Desktop 的 **Plugins / 插件** 中启用后，侧边栏会出现 **团队** 入口，Mission、队友和任务都在那块面板上。

![DotCraft Agent 团队](https://github.com/DotHarness/resources/raw/master/dotcraft/whats-new/teams.gif)

> [!NOTE]
> 每位队友都在自己的对话里工作，有独立的上下文、工具和历史记录。你可以打开任意队友的线程，完整看到它做了什么。

## 什么时候用团队

一件工作能舒服地塞进一条对话时，团队是过度设计。工作天然按角色拆开、任务之间有依赖，或者最后需要有人把结果综合成一份答复时，团队才用得其所。

| 场景 | 推荐 |
|---|---|
| 在已有对话中一次性委派独立任务 | [Subagents](./subagents) |
| 需要规划、并行推进并给出统一答复的请求 | Agent 团队 |
| 按计划或手动触发的例行工作 | [自动化与目标](./automations) |

## 固定的五个角色

| 成员 | 负责 |
|---|---|
| **Team Leader** | 拆解 Mission、分派任务、协调团队、写出最终答复。 |
| **Explorer** | 调研、勘察、理清未知项。 |
| **Builder** | 实施变更、产出工件。 |
| **Reviewer** | 检查质量、风险和正确性。 |
| **Operator** | 处理 App 和计算机相关的操作型任务。 |

成员是固定的，你不需要创建或移除谁。每位成员已经带好了适配自己那部分工作的角色设定和工具集。

## Mission 怎么推进

Mission 是你拿到手的交付单元：一块任务板，加上最后那份答复。Leader 先规划，再把任务派下去，全部完成后由它写出面向你的最终答复。

任务板上每条任务都带着执行人、状态、依赖和产出摘要，谁在做什么、卡在哪里一眼就能看清。Leader 派活时设定任务之间的依赖，也可以先审阅上游结果再放行下游工作。审核本身也是一条任务——任何成员都可以被指派去审核别人的工作。

Mission 结束后可以归档。归档保留记录，不会删除 Mission，也不会删除队友的线程。

> [!TIP]
> 取消和归档都是卡片动作：把 Mission 卡片拖进丢弃堆并确认。丢弃堆不是可点击的按钮，拖拽本身就是那个确认动作。

## 队友怎么协作

队友之间靠三种方式往来：

- **消息** —— 发给其他成员或 Leader 的轻量便条，用来提示某件事或请求输入。
- **工件** —— 显式交接：一份命名的结果，附上位置和简短摘要，让接手的队友清楚自己拿到的是什么。
- **进度更新** —— 中途状态或抛出的阻塞，让任务板保持最新。

Leader 不会一直盯着。派完活它就退到一旁，只有结果产出、出现阻塞、队友需要答复，或者 Mission 进入最终审核时才会被重新唤起。

Mission、任务和交接文件都存在工作区里，跟着项目走，换一个入口继续也还在。每个 Mission 还给队友留了一块共享草稿区，用来放需要反复取用的交接材料。
